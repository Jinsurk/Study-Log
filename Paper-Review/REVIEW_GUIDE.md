# 논문 리뷰 작성 가이드

이 문서는 다른 컴퓨터나 새로운 작업 세션에서도 Paper-Review의 구조와 작성 방식을 일관되게 유지하기 위한 안내입니다.

## 시작하기

1. 리뷰할 논문 원문을 확인합니다. 저자, 연도, 논문 버전, 방법과 실험 수치를 원문에서 확인합니다. 구조 설명에 필요한 그림(Fig.)과 수식은 PDF를 열어 직접 확인합니다.
2. 논문에 코드 링크가 있는지, 공개된 구현이 있는지 확인합니다. 확인 방법과 쓰는 방법은 [공식 코드 확인과 코드 대조](#공식-코드-확인과-코드-대조)를 따릅니다.
3. [리뷰 템플릿](./_template/review-template.md)을 사용하고, 분량과 구성은 [EWT 리뷰](./Image-Restoration/2023-EWT/)를 참고합니다.
4. 논문 주제에 맞는 분야 폴더를 선택합니다. 기존 분야에 넣기 어렵다면 적절한 새 분야 폴더를 만듭니다.
5. 리뷰 파일을 작성합니다. 원문 그림을 넣으려면 먼저 [그림과 이미지 사용](#그림과-이미지-사용)의 라이선스 확인 절차를 거칩니다.
6. [목록 README](./README.md)에 한 줄을 추가하고, 마지막에 [작업 후 점검](#작업-후-점검)을 확인합니다.

## 폴더 구조와 파일 이름

```text
Paper-Review/
├── README.md
├── REVIEW_GUIDE.md
├── _template/
│   └── review-template.md
└── Image-Restoration/
    └── 2023-EWT/
        ├── README.md
        └── images/             # 이미지가 필요할 때만 생성
            ├── fig2_ewt_architecture.png
            ├── fig4_dfeb.png
            └── fig5_convblock_transformer.png
```

- 리뷰 경로: `Paper-Review/분야/발표연도-모델명/README.md`
- 예: `Paper-Review/Image-Restoration/2023-EWT/README.md`
- 모델명이 불분명하면 짧고 알아보기 쉬운 논문 제목을 사용합니다. 연도는 검토한 논문의 공개·발표 연도를 확인해 기재합니다.
- GitHub는 빈 폴더를 저장하지 않으므로 `images/`는 실제 이미지가 필요할 때 만듭니다.
- 이미지 파일 이름은 `figN_설명.png` 형식으로, 영문 소문자와 밑줄만 사용합니다. 본문에서는 `./images/파일이름.png` 상대 경로로 참조합니다.

## 리뷰 작성 원칙

- 한국어로 작성하고 기술 용어와 모델명은 필요한 경우 원문 표기를 함께 사용합니다.
- 템플릿의 항목을 유지하되, 논문에 맞지 않는 항목은 그 이유를 간단히 적습니다.
- 연구 배경, 핵심 아이디어, 구조, 실험, 강점과 한계를 독립적으로 읽을 수 있도록 정리합니다.
- EWT 리뷰 정도의 밀도를 기본으로 하되 논문의 복잡도에 따라 조절합니다. 표와 간단한 흐름도를 활용할 수 있습니다.
- 수치에는 데이터셋, 실험 조건, 비교 모델 및 논문 표·그림 번호를 가능한 한 함께 적습니다. 서로 다른 조건의 결과는 직접 비교하지 않습니다.
- 논문이 주장하는 내용, 원문에서 확인한 결과, 리뷰어의 해석을 구분합니다. 확인하지 못한 사항은 추측하지 않고 미확인이라고 표시합니다.
- 실제 코드, 데이터, 발표 학회 또는 최신 버전을 확인하지 않았다면 확인한 것처럼 적지 않습니다. 논문 링크와 검토한 버전을 명시합니다.
- 「내 연구에 적용할 점」은 연구 아이디어로 표시하고, 논문에서 입증한 결과처럼 서술하지 않습니다.
- 논문 PDF는 저장소에 넣지 않고 원문 링크로 대신합니다. 그림은 [그림과 이미지 사용](#그림과-이미지-사용)의 조건을 확인한 뒤 필요한 영역만 사용합니다.

### 근거 표기

모델 구조처럼 원문 내용과 리뷰어의 해석이 섞이기 쉬운 부분은 문장마다 근거를 구분해 표시합니다. 절의 앞부분에 아래 표를 한 번 제시하고 본문에서 같은 표기를 씁니다. 모든 문장에 붙일 필요는 없고, 구분이 필요한 곳에 붙입니다.

| 표기 | 의미 |
|---|---|
| **[논문]** | 본문, 수식, 표에서 직접 확인한 내용 |
| **[그림]** | 원문 그림(Fig.)에서 확인한 내용 |
| **[해석]** | 위 근거에서 리뷰어가 구조적으로 추론한 내용 |
| **[예시]** | 이해를 돕기 위한 설명용 예시(실제 설정이 아님) |
| **[코드]** | 구현 저장소에서 확인한 내용(논문 버전과의 일치는 별도 확인 필요) |
| **[미확인]** | 논문, 그림, 코드로 확인되지 않은 내용 |

## 모델 구조 설명 작성법

「모델 구조와 동작 과정」절은 독자가 텐서의 흐름과 각 모듈의 설계 이유를 이해할 수 있도록 상세하게 작성합니다. [EWT 리뷰의 4절](./Image-Restoration/2023-EWT/)을 예시로 참고합니다. 템플릿의 4절은 아래 구성을 권장 구조로 삼되, 논문에 맞지 않는 부분은 줄이거나 생략하고 이유를 적습니다.

### 구성 순서

전체 구조 → 모듈 → 세부 연산 순서로 씁니다.

1. **전체 구조와 텐서 흐름:** 입력부터 출력까지의 흐름도와 단계별 텐서 크기 표
2. **모듈별 설명:** 각 모듈을 「입력 → 연산 → 출력 → 왜 필요한가」 순서로 설명
3. **세부 연산:** attention, 정규화, 손실 등 계산 과정을 입문자가 따라올 수 있게 설명
4. **효율·성능의 원인:** 구조의 어떤 부분이 측정값에 어떻게 연결되는지

### 작성 규칙

- **기호 정의:** 입력 크기(예: H×W×C)와 내부 차원(예: D)을 먼저 정의하고 일관되게 씁니다. 구체적인 숫자 예시는 **[예시]**로 표시합니다.
- **텐서 크기 표:** 열은 「단계 / 연산 / 출력 크기 / 근거」를 기본으로 합니다. 근거에는 수식 번호, 그림 번호, 절 번호를 적습니다. 원문이 크기를 직접 적지 않았다면 어떤 조건에서 추론했는지 적고 **[해석]**으로 표시합니다.
- **도식:** Mermaid로 그리고, 노드의 라벨은 원문 그림의 기호(Fe, Fin 등)를 그대로 씁니다. 그림에서 연결(합산인지 concat인지, 어디서 갈라지는지)을 직접 확인한 뒤 그립니다. 확인하지 못한 연결은 그리지 않습니다.
- **수식:** 원문의 수식 번호를 유지합니다. 이해를 돕기 위한 표기(예: ΔF)를 새로 쓰면 원문의 어느 기호에 대응하는지 밝히고, 해석임을 구분합니다.
- **용어:** 처음 쓰는 용어는 쉬운 뜻을 함께 적습니다.
- **저자의 설명과 일반적 해석 구분:** 설계 이유는 저자가 밝힌 설명과 일반적인 해석을 나누어 씁니다. 별도 실험이 없는 설정(예: 특정 하이퍼파라미터)을 최적이라고 쓰지 않습니다.
- **불일치 표시:** 본문, 그림, 코드가 서로 다르면 어느 한쪽으로 단정하지 않고 차이를 그대로 적습니다. 원문의 서술을 우선하고 코드는 참고로 둡니다.
- **구현 세부:** 논문으로 확인되지 않는 세부(필터 종류, 분할 방식, 마스크 사용 등)는 추측하지 않고 **[미확인]**으로 남깁니다. 코드에서 확인했다면 **[코드]**로 구분합니다.

### 자주 생기는 오해 점검

구조 설명을 쓴 뒤 아래 항목이 섞이지 않았는지 확인합니다.

- 합산(더하기)과 채널 concat의 구분. 논문이 "dense connection" 등의 표현을 써도 수식과 그림에서 실제 연산을 확인합니다.
- 같은 기호(N 등)가 다른 의미로 쓰인 경우의 구분
- 반복 횟수(블록 수)와 묶음(쌍) 수의 구분
- 값의 총개수와 처리하는 위치(토큰) 수의 구분. 효율 설명에서 「숫자가 줄어서 빠르다」처럼 쓰지 않습니다.
- 전체 영상 attention의 비용(토큰 수의 제곱)과 window attention의 비용 구조를 같은 것으로 설명하지 않습니다.
- 가역 변환(정보 보존)과 학습된 네트워크 전체의 정보 보존을 같은 것으로 쓰지 않습니다.
- 중간 출력(예: 잔차)을 곧바로 「노이즈 예측값」처럼 부르지 않습니다. 학습 손실이 어디에 걸리는지 확인한 뒤 서술합니다.
- 효율 수치는 측정 조건(모델 크기, 패치 크기, 측정 장비)과 표 번호를 함께 적고, 구조적 원인에 대한 설명은 **[해석]**으로 구분합니다.

## 그림과 이미지 사용

원문 그림은 이해에 도움이 되지만 재사용 조건을 먼저 확인해야 합니다. 이 저장소가 공개(public)인지 확인하고, 공개 저장소라면 공개 기준으로 판단합니다.

1. **라이선스 확인:** arXiv 논문 페이지(abs)에 표시된 라이선스를 확인합니다.
   - CC BY 등 재사용을 허용하는 라이선스: 출처와 라이선스를 표기하면 사용할 수 있습니다. 다른 CC 조건(NC, ND 등)이 붙어 있으면 조건을 읽고 따릅니다. 애매하면 사용하지 않습니다.
   - 라이선스가 표시되지 않았거나 arXiv의 기본 배포 라이선스만 있는 경우: 재사용이 허용된 것으로 보지 않습니다.
   - 저널·학회 출판본은 arXiv와 별도의 조건이 적용될 수 있습니다. 확인하지 않았다면 그렇게 적습니다.
2. **사용할 수 없을 때:** 원문 그림을 넣지 않고 직접 그린 도식(Mermaid 등)과 원문 그림 번호(Fig. N) 인용으로 대신합니다.
3. **필요한 영역만 사용:** 논문 쪽 전체가 아니라 해당 그림 영역만 잘라 씁니다. 인접한 캡션이나 본문 글자가 잘려 들어오지 않았는지 확인합니다.
4. **출처 표기:** 그림 바로 아래에 한 줄로 적고, 참고 자료에도 같은 내용을 기록합니다.

   ```markdown
   *그림 출처: 저자, [arXiv:번호vN](링크), Fig. N. 라이선스. 원문 PDF에서 해당 그림 영역만 잘라 사용했다.*
   ```

5. **파일:** `images/figN_설명.png`로 저장하고 수백 KB 이하를 권장합니다. 그림이 없는 논문은 `images/` 폴더를 만들지 않습니다.
6. **그림 설명:** 그림을 넣는 위치에 그림이 보여주는 내용과 주의점을 한두 문장 덧붙입니다. 그림에 표시되지 않는 사항(예: 분할 비율)을 그림에서 확인한 것처럼 쓰지 않습니다.

PDF에서 그림 영역을 잘라내는 예시입니다(PyMuPDF 필요). 좌표 단위는 포인트이며 쪽 번호는 0부터 시작합니다.

```python
import pymupdf

doc = pymupdf.open("paper.pdf")
page = doc[2]                                  # 3쪽
clip = pymupdf.Rect(40, 40, 580, 160)          # x0, y0, x1, y1
page.get_pixmap(matrix=pymupdf.Matrix(3, 3), clip=clip).save("fig2_architecture.png")
```

## 공식 코드 확인과 코드 대조

1. 논문 본문과 초록 페이지에 코드 링크가 있는지 확인합니다. 없으면 GitHub에서 논문 제목이나 모델명으로 검색합니다.
2. 저장소의 README가 "official"이라고 적고 있어도, 논문 저자의 계정인지, 논문 본문이나 저자 페이지가 그 저장소를 가리키는지 확인하기 전에는 「공식 구현이라고 스스로 밝힌 저장소」로 표기합니다.
3. 코드는 논문만으로 확인되지 않는 세부(분할 방식, 필터 종류, attention의 bias와 mask, 패딩 등)를 확인하고, 논문과 구현을 대조하는 데 씁니다. 대조 결과는 표로 정리하고 **[코드]**로 표시합니다.
4. 코드가 논문의 수식이나 그림과 다르더라도 논문의 오류로 단정하지 않습니다. 저널판이나 이후 버전의 차이일 수 있습니다. 저장소 주소, 확인한 날짜, 가능하면 커밋 해시를 적습니다.
5. 코드를 실행하지 않고 읽기만 했다면 그렇게 적습니다. 실행해서 재현했다고 쓰려면 실제로 실행한 환경과 결과를 적습니다.
6. 외부 저장소의 코드를 이 저장소에 복사하지 않습니다. 필요하면 링크와 필요한 설명만 적습니다.
7. 논문 정보의 「공식 코드」 항목에 확인한 결과(링크, 확인 날짜, 저자 소유 여부 미확인 등)를 적습니다.

## 다른 랩탑에서 작업하기

- GitHub에서 작업할 때는 이 가이드와 템플릿, EWT 예시를 열어 참고합니다. GitHub 계정에 저장소 접근 및 수정 권한이 필요합니다.
- 로컬에서 작업할 때는 저장소를 clone하거나 기존 저장소에서 최신 `main`을 pull한 뒤 작업합니다. 로컬 변경은 GitHub에 push하기 전까지 다른 랩탑에 자동으로 나타나지 않습니다.
- 기존 변경 사항을 먼저 확인하고 보존합니다. 변경을 공유할 때는 별도 브랜치와 PR로 검토할 수 있습니다.
- 작업 후 리뷰와 목록 링크가 올바른지, 원문 출처와 표의 조건이 들어갔는지 확인합니다.
- Windows PowerShell 5.1에서는 명령을 `&&`로 이을 수 없으므로 `;`를 씁니다(예: `git checkout main; git pull`). 명령은 저장소 폴더 안에서 실행합니다.
- OneDrive 폴더 안의 저장소에서는 git이 파일을 쓰다가 간혹 실패할 수 있습니다. 오류가 나면 `git status`로 상태를 먼저 확인합니다.
