# 실시간 자세 추정과 BLE 전송 (2026-10-08)

가속도계 20자세 보정 행렬과 정지 자이로 바이어스를 Arduino C++에 적용한 뒤, Roll·Pitch 계산, 상보 필터, 아이폰 15 Pro의 nRF Connect 수신까지 확인했다. 사용자가 보드를 기울였을 때 앱의 값이 계속 바뀌는 것을 확인했다. 이는 동작 확인이며 절대 각도 정확도 검증은 아니다.

## 실행 코드

- [imu_realtime.ino](arduino/imu_realtime/imu_realtime.ino): 시리얼 모니터(115200 baud) 연결 후 3초 대기, 초당 약 20행, 정확히 1,000행 출력 후 측정·출력 중단. RESET으로 다시 실행. 헤더는 출력하지 않는다.
- [imu_ble.ino](arduino/imu_ble/imu_ble.ino): USB 시리얼 연결을 기다리지 않는다. BLE 광고 시작 후 3초 대기하고 계속 측정한다. 초당 약 10회 각도 특성을 갱신한다. 1,000회 제한은 없다.
- 각 폴더의 accel_multi_calibration.h는 기존 20자세 모델의 복사본이다. 가속도 단위는 g, 각속도는 deg/s다. 가속도에는 중력이 포함된다.
- Arduino Nano 33 IoT, Arduino_LSM6DS3와 ArduinoBLE 사용. 두 최종 스케치를 Nano 33 IoT 대상으로 컴파일 확인했다. 보드 업로드 및 아이폰 연결은 사용자가 수행했다.

시리얼 최종 18열 순서:

```text
t_ms,ax_raw_g,ay_raw_g,az_raw_g,ax_cal_g,ay_cal_g,az_cal_g,accel_norm_g,gx_raw_deg_s,gy_raw_deg_s,gz_raw_deg_s,gx_cal_deg_s,gy_cal_deg_s,gz_cal_deg_s,roll_accel_deg,pitch_accel_deg,roll_filtered_deg,pitch_filtered_deg
```

이전 단계 캡처는 14열 또는 16열이다. t_ms는 MCU 실행 시작 기준이며 센서 내부 샘플 시각은 아니다. 가속도와 자이로는 최신 값을 각각 읽으며 하드웨어 동기화를 보장하지 않는다.

## 자이로 바이어스 갱신과 별도 검증

기존 바이어스 적용 후 정지 출력에 Y 약 -0.134336 deg/s, Z 약 +0.299747 deg/s가 남았다. 원인은 확정하지 않았다. [갱신용 캡처](data/gyro_refit_capture.txt)의 1,000행 중 쉼표가 빠진 370행을 제외한 999행의 원본 평균으로 바이어스를 갱신했다.

```cpp
constexpr float GYRO_BIAS[3] = {-0.01709710f, -0.63518519f, 0.37389389f};
```

[새 검증 캡처](data/gyro_refit_validation.txt)는 1,000행 모두 정상이다. 보정 후 각속도 평균은 X +0.003727, Y -0.003775, Z -0.002894 deg/s였다. 가속도 크기 평균은 0.999373 g, 1g 대비 RMSE는 0.000813 g였다. 검증 데이터로 바이어스를 다시 맞추지 않았다. 온도·재부팅에 따른 안정성이나 자이로 스케일은 별도 검증이 필요하다.

## Roll·Pitch의 의미와 계산

Roll은 센서 X축 회전, Pitch는 Y축 회전이다. 비행기의 날개가 좌우로 기울어지는 움직임이 Roll, 기수가 올라가거나 내려가는 움직임이 Pitch에 해당한다. 센서 +Z 방향이 위인 정지 자세를 Roll=Pitch=0 기준으로 사용한다.

```cpp
roll  = atan2f(ay, az) * 180 / PI;
pitch = atan2f(-ax, sqrtf(ay*ay + az*az)) * 180 / PI;
```

보정된 가속도를 사용한다. 이번 장착에서는 USB 쪽을 들어 올릴 때 Pitch가 주로 변했다. 센서 축 기준이므로 보는 방향만으로 앞뒤·좌우를 정하지 않는다. 중력으로 Yaw를 구할 수 없으며, 직선 가속도와 진동은 가속도 기반 기울기를 흐트러뜨린다.

| 캡처 | 유효 행 | Roll 평균 | Pitch 평균 | 평균 가속도 크기 |
|---|---:|---:|---:|---:|
| [평평한 자세](data/tilt_flat_capture.txt) | 999 | +0.726802° | +0.338197° | 1.000261 g |
| [USB 쪽을 들어 올림](data/tilt_usb_raised_capture.txt) | 999 | +2.601455° | -6.988710° | 0.999996 g |

각 캡처의 608행, 88행은 형식 오류로 제외했다. 수평 기준 장비가 없으므로 평평한 자세의 잔여 각도를 모두 센서 오차로 해석하지 않는다. 같은 기울임 캡처를 두 번 제출한 경우 한 번만 포함했다.

## 상보 필터

센서 값을 읽을 때마다 micros()의 실제 시간 차 dt로 자이로를 적분하고, 가속도 기울기를 섞는다. 출력 주기와 필터 갱신 주기는 분리했다. 첫 각도는 가속도 값으로 초기화한다.

```text
alpha = 0.5 / (0.5 + dt)
angle = alpha * (previous_angle + gyro_rate * dt)
      + (1 - alpha) * accel_angle
```

Roll 오차는 ±180° 경계를 감아 처리한다. gx, gy를 Roll·Pitch 변화율로 사용하는 작은 기울기 근사이며, 큰 기울기·여러 축의 동시 회전에는 일반적인 3D 자세 추정기가 필요하다. 가속도 크기에 따른 측정 제외 기능은 아직 없다.

[상보 필터 캡처](data/complementary_capture.txt)의 Pitch는 약 -40°까지 변한 뒤 약 -14.5°에 머물렀다. 마지막 정지 구간(데이터 301~1000 중 이상값 1개 제외, 699개)의 비교:

| 각도 | 가속도 평균 / 표준편차 | 필터 평균 / 표준편차 |
|---|---:|---:|
| Roll | 2.715283° / 0.066985° | 2.714498° / 0.007322° |
| Pitch | -14.476306° / 0.048222° | -14.481004° / 0.011387° |

정지 출력의 흔들림 감소를 확인했다. 동적 정확도·응답 지연을 기준 장비와 비교한 결과는 아니다. 캡처에는 이전 실행 또는 재시작으로 추정되는 초기화 오류 문구와 1,000개 데이터가 함께 있다. 현재 코드는 초기화 실패 시 멈추므로 같은 실행에서 이어지는 출력일 수 없다. 원본 965행 마지막 값 -14485는 소수점 3자리 출력 형식과 맞지 않아 통계에서 제외했다. 붙여넣기 손상인지 통신 손상인지는 확정하지 않았다. 원문은 수정하지 않았다.

## 아이폰 BLE 확인

1. imu_ble 스케치를 업로드하고 USB 등으로 전원을 공급한다.
2. nRF Connect에서 Nano33-IMU를 검색하고 연결한다. iOS 설정에서 별도 페어링하는 과정은 필요하지 않았다.
3. 서비스 7f510001-1b15-4b3b-8a54-73251f861234를 펼친다.
4. 특성 7f510002-1b15-4b3b-8a54-73251f861234의 Notify를 구독한다. 특성 속성은 Read, Notify다.
5. UTF-8/Text로 해석하면 R:2.71,P:-14.48처럼 보인다. R은 Roll, P는 Pitch이며 단위는 도다.

ASCII 문자열은 최대 20바이트 특성으로 보낸다. 아이폰 연결 및 값의 지속적인 변화까지 사용자가 확인했다. LED는 연결 상태에서 켜진다. 재연결 시 앱에서 Notify 구독 상태를 확인한다. 시리얼 모니터 없이도 동작하지만 전원은 계속 필요하다.

## 남은 작업

- 전원 재인가·온도 변화에 따른 자이로 바이어스 반복 검증.
- 기준 각도와 동적 움직임을 이용한 자세 추정 오차·지연 평가.
- 큰 기울기와 여러 축 회전에 대응하는 자세 추정, 센서 축 정렬 확인.
- Wi-Fi 전송 및 IMU–카메라/LiDAR의 공간·시간 외부 보정은 아직 진행하지 않았다.
